# Milestones — rover MVP

The MVP: anyone can open a link, **build** a wheeled rover from parts,
**program** it, run it in an **environment**, and **share** a link that
anyone can **remix**. Wheeled rovers first; arms and legs come later.

Rules for agents (see `CLAUDE.md`):

- Work on the **first milestone that isn't done**. One milestone per PR.
- Tick a box only when it's done *and* tested. Leave a short note under
  "Progress notes" when you stop partway.
- If a milestone is too big for one session, finish a coherent subset, tick
  what's done, and note what's left. The next run continues it.
- Acceptance criteria are the contract. If one is wrong or impossible, say so
  in the PR instead of quietly changing it.

---

## M0 — Harness + skeleton ✅

- [x] Vite + TypeScript (strict) app, deployed to GitHub Pages by Actions
- [x] MuJoCo WASM wrapper usable in Node and the browser
- [x] Three.js renderer for primitive geoms; hello-world scene with a drivable rover
- [x] Unit tests: settling, determinism, reset, driving direction, instability detector
- [x] Browser tests: loads without errors, drives (API + keyboard), perf budget, phone layout, screenshots
- [x] CI runs typecheck, unit, build and browser tests on every PR

## M1 — Load and render any MJCF ✅

Goal: the viewer is a general MuJoCo viewer, not just one scene.

- [x] Renderer supports `mesh` geoms (build `BufferGeometry` from `model.mesh_vert` / `mesh_face`) and per-geom materials/colors
- [x] Bundled sample scenes: hello rover, a 2-link arm, a cart-pole; a scene picker in the header (`?scene=<id>` in the URL selects one)
- [x] Load a user's single-file MJCF (`.xml`) by file picker and drag-and-drop; show a friendly error (not a crash) for invalid files
- [x] Drive pad only appears when the scene has `left`/`right` actuators
- **Acceptance:** e2e loads every bundled scene with no console errors and ≥ 80% real time; e2e loads a fixture `.xml` through the file input; an invalid file shows an error message and the previous scene keeps running; unit test that each bundled scene compiles and stays stable for 5 s.

## M2 — Parts → MJCF compiler ✅

Goal: robots are described as simple JSON and compiled to valid MJCF. This is the core of the product.

- [x] `src/robot/spec.ts`: `RobotSpec` type (chassis, wheels, motor, caster, sensors) + validation returning readable errors
- [x] `src/robot/parts.ts`: ~10 pre-tuned parts: 3 chassis sizes, 2 wheel sizes, 2 motors (fast / strong), caster ball, distance sensor (rangefinder), line sensor (downward rangefinder or color probe). Physically sensible masses, frictions, torques.
- [x] `src/robot/compile.ts`: pure function `compile(spec) → MJCF string`. Always uses `implicitfast`; actuators named `left`/`right`; sensors named predictably.
- [x] 3 templates (`src/robot/templates.ts`): "Scout" (small, fast), "Hauler" (big, strong), "Sensor bot" (with distance + line sensors)
- [x] Hello scene's rover replaced by a compiled template
- **Acceptance:** unit tests compile *every* combination of chassis × wheels × motor (with and without sensors) and each one: compiles, settles upright, drives forward ≥ 0.3 m in 2 s, never becomes unstable. Golden trajectories for the 3 templates (`tests/golden/`, generated by a script, checked in) with a tolerance test. Invalid specs give errors, never throw from inside MuJoCo.

## M3 — Builder UI ✅

Goal: a beginner builds a rover without touching code or files.

- [x] Side panel (bottom sheet on phones): start from a template, pick chassis / wheels / motor, toggle sensors
- [x] Every change recompiles and reloads the sim instantly, keeping camera position
- [x] Validation errors shown inline in plain language
- [x] Fully keyboard-accessible and labeled for screen readers
- **Acceptance:** e2e builds a rover from scratch through the UI only (clicks, no test hooks for building), drives it forward, and asserts it moved; same flow passes on a 390×844 touch viewport; screenshot of the panel on desktop and phone.

## M4 — Controller sandbox ✅

Goal: make the robot do things by itself.

- [x] User JavaScript runs in a Web Worker with a tiny API: `robot.setWheels(left, right)`, `robot.read(sensorName)`, `robot.time`; called each control tick (50 Hz)
- [x] Code editor panel with 3 example programs (drive in a square, avoid obstacles, follow a line)
- [x] Safety: an infinite loop or exception never freezes the page; worker is restarted and the error shown with a line number
- [x] Blocks editor (Blockly) that generates the same JS; switch between blocks and code view
- [x] Python is a stretch goal (Pyodide, lazy-loaded) — only if it keeps the perf budget
- **Acceptance:** unit tests for the controller API against the compiled template; e2e runs each example program and asserts its effect (square returns near start; avoider doesn't hit a wall in 10 s); e2e with `while(true){}` shows an error and the page stays responsive.

## M5 — Environments ✅

Goal: something to do.

- [x] Environments as data (`src/envs/`): flat playground, maze, line-follow track, sumo ring
- [x] Each environment has a goal, a timer, and a success/fail banner (maze: reach the exit; line: finish a lap; sumo: push the box out)
- [x] Environment picker; the robot spawns at the environment's start pose
- **Acceptance:** for every environment a *reference controller* (checked in under `tests/`) completes the goal in a unit test (Node, no browser), so we know each one is solvable; e2e switches through all environments with no errors and ≥ 80% real time.

## M6 — Share + remix ✅

Goal: a link is the whole sim.

- [x] Serialize robot spec + controller code + environment into the URL fragment (`#s=…`), compressed (`CompressionStream` deflate + base64url). No backend.
- [x] "Share" button copies the link; "Remix" makes clear you're editing a copy (shows "Remixed from …" with the parent link)
- [x] Opening a link restores the exact sim; malformed links show a friendly error and fall back to the default scene
- [x] Links stay under ~2,000 characters for typical robots
- **Acceptance:** unit round-trip tests (serialize → parse → deep equal) including unicode code; e2e builds a robot, writes code, shares, opens the link in a fresh page, and gets the same spec, the same code, and the same trajectory (determinism); an e2e for a corrupted link.

---

When M6 is merged, the MVP is done. Next ideas (not scheduled): weekly
challenges and leaderboards, arms, legged robots, Python, WebSerial bridge to
real hardware.

  works (meshes must be inline `vertex=`; `file=` references give a friendly
  "another file" error). Height fields are not drawn yet. `Sim.actuatorNames()`

- 2026-11-03 (M2): done. Notes for later milestones:
  - Wheel `ctrl` is a target wheel speed in rad/s (velocity actuators); the
    drive pad's full stick is the motor's top speed (`driveTopSpeed`, capped
    at 30 rad/s). M4's `robot.setWheels` should decide whether to expose
    rad/s or a −1…1 fraction of top speed.
  - Robots have two ball casters (front and back, lifted 3 mm) with the
    wheels in the middle, so they turn on the spot and can't tip either way.
  - The line sensor is two downward rangefinders: they read height, not
    colour. M5's line track should be thin non-colliding strips
    (`contype="0" conaffinity="0"`, a few mm tall) that the probes see as a
    drop in distance (see the line-sensor test in `tests/unit/robot.test.ts`).
  - The distance sensor reads -1 when nothing is in range.
  - `compile(spec, { pose, world })` places the robot and adds environment
    props; `world` is trusted MJCF. `npm run golden` regenerates
    `tests/golden/templates.json` (protected: only for intended physics changes).
  - The Hello scene uses the Hauler template: the protected hello test spins
    at ±10 rad/s for 1 s and expects yaw in (0.3, π), which faster-spinning
    templates (Scout) overshoot.
- 2026-11-04 (M3): done. Notes for later milestones:
  - The builder lives in `src/ui/` (`builder.ts` DOM, `builderModel.ts` pure
    logic). Its robot runs as scene id `"build"` ("My robot: <name>" in the
    picker); it isn't in the URL yet (M6 should put the spec in `#s=`).
  - `BuilderPanel.spec` is the last valid spec built; M4/M6 can read it.
  - Arrow keys don't drive while focus is inside `[data-no-drive]` (the
    builder), because they move between radio buttons there.
  - Use `cloneSpec()` (src/robot/spec.ts), not `structuredClone`: iOS Safari

- 2026-11-05 (M4, part 1): done: Web Worker sandbox, code panel with 3
  examples, safety (watchdog + line numbers). Left: the Blockly editor
  (and the optional Python stretch goal). Notes:
  - Code lives in `src/control/`: `program.ts` (runs the program; the code
    inside the worker), `controller.ts` (lockstep with the sim), `host.ts`
    (the Worker + watchdog), `examples.ts`. The panel is `src/ui/codePanel.ts`.
  - Program shape: top-level code runs once on the first tick; a top-level
    `function loop() {}` runs every tick (50 Hz). `robot.setWheels(l, r)`
    takes -1..1 (fraction of the motor's top speed, i.e. the actuator's
    upper ctrlrange capped at 30 rad/s); `robot.time` is seconds since the
    program started (1/50 s per control tick); `console.log` shows in the panel. Blockly
    should generate this same shape.
  - Lockstep: physics holds at every control tick until the worker answers
    (`SimLoop` `beforeStep` returning false + `pump()`), so runs are
    deterministic regardless of device speed. M6 can rely on that.
  - Run resets the scene; Reset restarts a running program; changing the
    scene stops it. A tick that takes over 1 s (5 s for the first, which
    also loads the worker and runs the top-level code) terminates the
    worker and stops the program with an error (no line number for that);
    the next Run starts a fresh worker. Replies are checked (`parseReply`)
    and the worker removes `postMessage` and network APIs before user code
    runs, since M6 links will run other people's code.
  - Bundled "Sensor playground" scene (`?scene=sensors`): Sensor bot in a
    3 m walled pen with a circular line (radius 0.8 m). M5 may fold it into
    the environments.
  - The worker is a classic (not module) worker so Firefox < 114 works; it
    bundles acorn (~120 KB, loaded only on first Run) to find syntax error lines.
- 2026-11-06 (M4, part 2): Blockly editor done. Left in M4: only the
  optional Python stretch goal (owner to decide whether it blocks M5).
  Notes:
  - Blocks view = `src/ui/blocksEditor.ts` (DOM, lazily `import()`ed on the
    first switch to Blocks, ~220 KB gzip) + `src/control/blocks.ts` (block
    definitions, toolbox, block versions of the examples, and
    `blocksToCode()` / `workspaceToProgram()`, headless, unit-tested in
    Node). Nothing else may import either eagerly (a unit test checks).
  - Blocks generate into the same textarea: "when the program starts" →
    top-level code, "every tick" → `function loop()`. Blocks outside those
    hats are greyed out and don't run. Code can't be turned back into
    blocks: switching back after editing the code asks first. M6 should
    share the blocks workspace JSON (`BlocksEditor.save()`) when the Blocks
    view is in use, not only the generated code.
  - Blockly's images/cursors are served from `public/blockly-media/` (no
    CDN requests; an e2e test checks).
  - No "repeat while" block: sensors only change between ticks, so it
    would loop forever. Escape inside a Blockly menu closes the menu only.
  - `SimLoop` now skips drawing while a program holds physics, is more than
    50 ms behind and drawing is slow (> 50 ms per frame), drawing at least
    every 250 ms; `stats.fps` counts frames drawn. On software-rendered
    Chrome (~150 ms per frame) each worker round trip waited a whole frame,
    so programs ran at ~20% real time. The "running program keeps real time"
    e2e failed on `main` in this environment before the fix.
- 2026-11-08 (M4, part 3): Python done; M4 is complete. Notes:
  - Code view has a "Language" menu (JavaScript / Python); each language
    keeps its own code while the other shows; Blocks always make JavaScript
    (opening Blocks switches the menu back). M6 should share the language
    with the code.
  - Python API: `robot.set_wheels(l, r)` (`setWheels` also works),
    `robot.read(name)`, `robot.time`, `print()`; `def loop():` runs every
    tick. `src/control/python.ts` is the runner (pure; unit-tested on real
    Pyodide in Node); the Python versions of the examples drive exactly the
    same trajectory as the JavaScript ones (a unit test checks qpos equality).
  - Pyodide (pinned exact version in package.json, ~12 MB, ~6 MB gzipped)
    is served from our own site under `/pai-sim/pyodide/` by a small Vite
    plugin in `vite.config.ts` (copied from node_modules at build). Nothing
    downloads until a Python program runs; physics waits at the first tick
    while it loads (status "Loading Python…"), with a 120 s load timeout.
  - `src/control/pyWorker.ts` is a *module* worker (Pyodide's loader
    rejects classic workers), and Pyodide itself needs a recent browser
    (Firefox 114+ for module workers; only Chrome is tested here); older ones get a friendly "Python couldn't start" error and
    JavaScript/Blocks still work. Network/messaging APIs are blocked after
    Pyodide loads, before user code runs (`src/control/workerSafety.ts`,
    shared with the JS worker). Each run uses a fresh worker, so Reset
    re-initialises Python (a few seconds; files come from the HTTP cache).
- 2026-11-09 (M5): done. Notes for M6 and later:
  - `src/envs/`: one file per environment (`playground`, `maze`, `line`,
    `sumo`), each an `Environment` (id, name, goal text, time limit, start
    pose, world MJCF, sensors it needs, suggested template, `createGoal()`).
    `GoalTracker` (`goal.ts`) latches the first success/fail, applies the
    time limit, and starts a fresh attempt when sim time goes backwards
    (Reset, Run). The clock starts only when the robot first moves 2 cm
    from its spawn point (time spent writing a program doesn't count), and
    the reported time is from then. Goals read state through `EnvView` (`simView(sim)`), so
    they are pure and unit-tested in Node.
  - The "My robot" scene (`build`) is now the builder's robot *in an
    environment* (default: Playground, which is the old empty floor plus a
    target circle). The header's "Environment" picker (`#env-picker`)
    switches it; `?env=<id>` opens it with the environment's suggested
    template. The goal is checked before every physics step (in the loop's
    `beforeStep`), so it can't be skipped on slow frames. M6 should share
    the environment id along with the spec and code.
  - Reference controllers live in `tests/envs/reference.ts` (plain user
    JavaScript for a stock template); `tests/unit/envs.test.ts` runs each
    to success, and the e2e runs two of them through the code panel.
  - The maze reference uses timed 90° turns tuned for the Sensor bot; if
    parts or physics change, retune `QUARTER` there (not the test).
  - The old "Sensor playground" scene is still there; the line track and
    maze cover similar ground, so it could be folded in later.
- 2026-11-10 (M6): done; the rover MVP is complete. Notes for later:
  - `src/share/link.ts` (pure): `#s=<format><base64url>`, format "1" =
    deflate JSON (`CompressionStream`), "0" = plain JSON for browsers
    without it. State: `{ v: 1, robot + env | scene, program: { language,
    code, blocks? }, parent? }`. `decodeShare()` never throws; it validates
    the spec (`validateSpec`), env/scene ids, sizes (payload, inflated JSON,
    code) and the blocks JSON's shape (`blocksLookSane`), and drops a broken
    parent. Bump `SHARE_VERSION` only with a migration: old links must keep
    opening.
  - Remix: a link opened and changed records the opened link's core as
    `parent` (one level only, so links don't grow with each remix; deflate
    makes the shared program nearly free). Unchanged sims re-share the same
    link. The remix bar (`src/ui/share.ts`) shows "Remixed from …" and, for a
    remix of a remix, its parent.
  - Blocks are shared as the workspace JSON without block ids
    (`stripBlockIds`), plus the generated code. Blocks from a link are shown
    (and their code regenerated) before they run, so what runs is what the
    blocks say. A model opened from a file can't be shared (the dialog says so).
  - Changing the sim after opening a link removes `#s=` from the address
    bar, so a reload keeps the change. Pasting a link into an open tab
    reloads the page (`hashchange`).
  - `__paiSim.programTrace()` records [time, rover xyz, qpos…] per physics
    step from Run; the e2e uses it to check a shared sim drives identically.
  - Typical links are 650–900 characters (blocks: ~1,000–1,400; remixes of
    typical robots stay under 2,000).
